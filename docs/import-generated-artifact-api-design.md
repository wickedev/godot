# 임포트 파생 아티팩트 API — 설계 초안 (구현 전 승인 요청)

> **상태: 초안.** 리뷰 승인 전까지 구현하지 않는다.
> 태스크 #26. 이전 시도 2회(`maintainer/l1-post-import-gen-files` v2/v3)는 **조사용으로 보류**하고 병합하지 않는다.

## 0. 왜 다시 쓰는가

원래 요구는 "임포트 후처리 훅이 만든 파생 아티팩트(Nanite 클러스터 DAG 등)를 엔진이 추적하게 하라"였다. 첫 두 시도는 기존 `r_gen_files` 목록에 경로를 등록하는 얇은 API였고, 리뷰가 그 방향 자체를 기각했다. 기각 사유가 옳다:

**평범한 `res://` sidecar는 `ImportTransaction` 밖이다.** 경로 검증을 아무리 강화해도 원자적 커밋/롤백, 세션 격리, 다중 에디터 충돌, 선택 익스포트가 **구조적으로** 해결되지 않는다. v2 → v3에서 내가 두 라운드를 경로 검증에 쓴 것은 **잘못된 API를 더 안전하게 만드는 작업이었지 목적에 맞게 만드는 작업이 아니었다.**

기각된 API가 실제로 제공하던 것은 `[deps] dest_files` 기록 하나뿐이었고, 나는 거기서 자동 삭제·의존성·익스포트 포함을 **추론**해 문서에 썼다. 셋 다 성립하지 않았다.

## 1. 계약

플러그인은 **경로를 고르지 않는다.** 임포터가 할당한다.

| 단계 | 주체 | 내용 |
|---|---|---|
| ① 할당 | 임포터 | 플러그인이 소스 상대 이름 + 확장자를 요청 → 임포터가 **private staging 물리 경로** + **logical final path/identity handle** 할당 |
| ② 기록 | 플러그인 | **staging 물리 경로에만** 쓴다. logical 경로에는 쓸 수 없다 |
| ③ 커밋 | 임포터 | `_post_process` 정상 반환 시 `ImportTransaction`이 **존재·크기·해시를 검증**하고 generation과 함께 **원자 publish** |
| ④ 실패 | 임포터 | 검증 실패·기록 실패·플러그인 오류 → **import 전체 실패**로 전파, staging 폐기, publish 없음 |

**충돌은 할당 단계에서 실패한다.** 두 플러그인이 같은 identity를 요청하면 두 번째 요청이 실패한다 — 기록이 일어나기 전이므로 덮어쓸 것이 없다. (v3는 기록이 끝난 뒤에 등록해서 덮어쓰기를 막을 수 없었다.)

## 2. 오류 전파

`add_generated_file(): void`의 근본 문제는 **거부가 진단일 뿐**이었다는 것이다. `Error` 반환을 추가해도 부족하다 — `_post_process` 자체가 void이고 기록이 이미 끝난 뒤라 원자성이 없다.

- 할당은 **핸들 또는 실패**를 반환한다.
- 임포터가 커밋 단계에서 검증하므로, 플러그인이 오류를 무시해도 **import가 실패한다.**
- 즉 실패 전파가 플러그인의 성실성에 의존하지 않는다. 이것이 v3와의 핵심 차이다.

## 3. 생애주기

| 사건 | 동작 |
|---|---|
| 정상 임포트 | staging → 검증 → 원자 publish, generation 기록 |
| 임포트 실패 | staging 폐기, 이전 generation 그대로 |
| 재임포트, 같은 아티팩트 | 새 generation으로 교체 (원자) |
| 재임포트, 아티팩트 미요청 | 이전 것을 **orphan GC 대상**으로 표시 |
| 두 에디터 동시 | staging이 세션별이므로 격리; publish는 generation으로 직렬화 |

## 4. 익스포트·의존성

**여기서 과장하지 않는다.** publish된 아티팩트가 익스포트에 포함되려면 **저장된 씬 또는 그 리소스가 실제로 참조**해야 한다. API는 logical path/UID를 제공하고, **참조를 만드는 것은 플러그인의 책임**이다. API가 자동으로 익스포트 포함을 보장한다고 쓰지 않는다.

## 5. 훅 위치

`_post_process`는 per-node 메시에 대해 late이다 — 언랩·LOD 생성 뒤다. **그러나 보편적 최종 단계가 아니다**: 뒤 플러그인이 mutate할 수 있고 single-mesh merge/packaging은 모든 플러그인 뒤에 온다. 따라서 "final mesh 보장"을 주장하지 않으며, 그 보장이 필요하면 **별도 finalization 훅**이 선행 안건이다.

## 6. 테스트 행렬 (병합 조건)

| # | 시나리오 | 확인 |
|---|---|---|
| 1 | allocate → write → publish | logical 경로에 나타나고 generation 기록 |
| 2 | 커밋 전 실패 | staging 폐기, 이전 generation 유지, publish 없음 |
| 3 | 플러그인이 아무것도 안 씀 | 커밋 검증이 실패로 잡음 |
| 4 | 재임포트 교체 | 원자적 교체, 중간 상태 관측 불가 |
| 5 | 재임포트 미요청 | orphan GC 대상 표시 |
| 6 | 두 플러그인 동일 identity | **할당 단계**에서 두 번째 실패 |
| 7 | 두 세션 동시 | staging 격리, publish 직렬화 |
| 8 | traversal / alias | 플러그인이 경로를 고르지 않으므로 **표면 자체가 없음** — 그 사실을 테스트로 고정 |
| 9 | 저장 리소스 참조 + 선택 익스포트 | 참조가 있을 때만 포함됨 |

**⑧이 v3 대비 가장 큰 개선이다.** v3는 `res://../outside` 같은 이스케이프를 검증으로 막아야 했고, `simplify_path()`가 res:// 선행 `..`를 의도적으로 보존하기 때문에(`ustring.cpp:4218` FIXME) 그 검증은 원리적으로 containment가 될 수 없었다. **경로를 플러그인이 고르지 않으면 그 공격면이 존재하지 않는다.**

## 7. 미해결 — 승인 시 답이 필요한 것

1. **staging 물리 위치.** `.godot/imported` 하위인가, 별도 트리인가. `ImportTransaction`의 기존 staging과 같은 메커니즘을 쓰는가.
2. **identity 키.** 소스 UID + 요청 이름으로 충분한가. 소스 경로 변경 시 identity가 따라가는가.
3. **GDScript 표면.** 스크립트 플러그인이 물리 staging 경로를 직접 받는가, 아니면 쓰기도 API를 거치는가. 직접 주면 플러그인이 그 경로를 저장·재사용할 수 있고 그게 다시 구멍이 된다.
4. **기존 `r_gen_files`와의 관계.** 새 경로로 통합하는가, 병존하는가.
